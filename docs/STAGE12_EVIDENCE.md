# 12단계 총공세 실측표와 기록 절차

이 표는 **시험 계획**이며 판정 결과가 아니다. `미실행`은 통과나 실패를 뜻하지 않는다. 아래 22개 정상·금지 사례는 41종 운영 공격의 전체 목록이 아니다. 저장소에는 운영 41종의 개별 요청 ID와 결과가 없으므로 41종 통과 수는 **미확인**으로 둔다.

## 기록 절차

1. 시험할 배포의 URL과 Git 커밋을 먼저 확인한다. 이전 배포의 응답을 새 커밋의 결과로 옮기지 않는다. 시험 계정·승인 기기는 공식 화면에서 준비하고 비밀번호·토큰·쿠키·메모 본문을 표나 로그에 복사하지 않는다.
2. 각 행을 **하나씩** 실제 API 또는 운영 ALEPH SDP 엔진으로 실행한다. 정상 요청은 승인된 시험 계정의 소유 메모만 사용한다. 타인 자료 시험은 별도 시험 계정과 사전에 허가된 가상 메모만 사용한다. 복구·삭제처럼 상태를 바꾸는 요청은 별도 승인된 시험 자료가 없으면 실행하지 않는다.
3. 브라우저 개발자 도구의 Network 또는 승인된 서버 기록에서 메서드·경로·HTTP 상태(엔진이면 결정/동작)만 읽는다. `X-Request-Id`가 있으면 그 값을 적고, 없으면 플랫폼의 `x-vercel-id`를 적는다. 둘 다 없으면 `요청 ID 없음`이라고 적는다. **클라이언트가 만든 임의 ID를 서버 ID로 쓰지 않는다.** 응답을 확인한 UTC 시각을 ISO 8601로 적는다.
4. `실제 API/엔진 결과`에는 `HTTP 403 DEVICE_SESSION_REQUIRED` 같은 상태와 오류 코드, 또는 엔진의 `deny`/`allow`/`step_up`만 적는다. 응답 본문·사용자 ID·토큰은 적지 않는다. 기대와 일치할 때만 별도 판정란에 통과라고 적는다. 실행하지 않은 행은 계속 `미실행`이다.
5. 작전실의 `요청 ID`로 Vercel Runtime Logs의 `operations_summary` 한 줄을 찾는다. 화면의 규칙 수·탐지 사건 수·회수/복구 실행 상태가 **같은 요청 ID**의 가린 서버 기록과 일치하는지 대조한다. 로그가 없으면 `대조 미실행`이다. 이 기록은 화면 메타데이터의 일치만 증명하며 운영 판정기의 공격 방어 성공을 증명하지 않는다.
6. 41종 운영 총공세는 판정기가 제공한 **개별 케이스 ID, 요청 ID, 확인 시각, 결과**가 확보된 것만 별도 41행으로 기록한다. 공식 41종 목록이 제공되기 전에는 22행 표를 41종 시험으로 바꾸거나 미실행을 통과로 세지 않는다.

`실제 API/엔진 결과`의 초기값은 전부 `미실행`이다. 로컬의 `npm run decider:test`와 `npm run detect:test`는 가상 계약 검사일 뿐 운영 결과가 아니다. 현재 복구 API는 검증된 사본이 없어 코드상 차단되며, 정상 복구 시험은 진행하지 않는다.
